# Erudi Backend — Requirements

Dependencies are split per platform/hardware to keep each build minimal and
reproducible. Composition is layered: an **entrypoint** pulls in shared **meta**
modules (`-r ...`). What a release build installs is **locked**: every package
of each prod entrypoint's resolution, transitive ones and the build tool
included, is pinned in `lock/`.

## Layout

```
requirements/
├── entrypoints/
│   ├── dev/                  # prod + dev tools (pytest, ruff, …)
│   │   ├── mac-silicon.txt
│   │   ├── linux-cpu.txt
│   │   ├── linux-cuda.txt
│   │   ├── win-cpu.txt
│   │   └── win-cuda.txt
│   └── prod/                 # minimal runtime deps (one per platform, *-prod.txt)
├── lock/                     # GENERATED: the resolved set of each prod entrypoint
│                             #   + meta/build.txt, same file name (lock/win-cpu-prod.txt, …)
├── meta/
│   ├── base.txt              # shared core: FastAPI, SQLAlchemy, pgserver,
│   │                         #   langchain, sentence-transformers, transformers (pinned 5.14.1)
│   ├── build.txt             # the build tool (PyInstaller); in no entrypoint, locked with each prod one
│   ├── dev.txt               # pytest / ruff (linter + formatter) / mkdocs
│   ├── cpu.txt               # CPU torch (official CPU index) + gguf — REUSED by the CUDA entrypoints
│   ├── cuda-specs.txt        # CUDA-only non-torch bits (pynvml). No torch+cuXXX.
│   ├── cuda-win-specs.txt    # Windows CUDA build tools (cmake)
│   ├── linux-specs.txt
│   ├── mac-silicon-specs.txt # MLX (mlx-vlm + mlx, both pinned)
│   └── win-specs.txt         # Windows-only (currently none)
```

## Declared and locked

- **Declared**: `meta/` and `entrypoints/` say what the backend needs — its
  direct dependencies, pinned, plus the platform specifics. A transitive package
  is never declared just to hold its version.
- **Locked**: `lock/<entrypoint>.txt` holds the index options of the
  requirement files (the PyTorch CPU index), then every package the prod
  entrypoint and `meta/build.txt` resolve to together on its platform, sorted,
  as `name==version --hash=sha256:<hash>`: the hash of the one file pip selected
  for that platform. It is generated by `scripts/dev/lock_backend_requirements.py`
  and never edited by hand.

`scripts/ci/install_backend_requirements.sh` (release.yml and
app-build-smoke.yml) creates a fresh venv, installs the lock alone into it in
hash-checking mode (`pip install -r lock/<entrypoint>.txt --require-hashes
--no-deps`), runs `pip check`, then `scripts/ci/check_backend_lock.py installed`
fails the step unless the venv holds exactly the lock (pip aside, which the venv
brings). The venv keeps the runner's own Python packages (pipx and its
dependencies on Windows) out of the build. So a rebuild bundles the files of the
tested build: a package published the day before a build does not reach it, nor
does a wheel added later to a locked version (a new build tag or platform tag),
and the smoke on `ubuntu-latest` installs the same files as the release on
`ubuntu-22.04`. This matters most for native wheels — an unsigned `.pyd`
published hours before a build has no reputation yet, and Windows Smart App
Control, enforced on many fresh Windows 11 installs, refuses to load it — and for
the build tool: PyInstaller's bootloader becomes the backend executable, and its
hooks (`pyinstaller-hooks-contrib`) decide what the bundle carries.

Each lock is resolved for the machine its build runs on, with the tags its pip
accepts in its order of preference — `win_amd64`; manylinux up to the glibc of
`ubuntu-22.04`, the oldest Linux release runner, so the hash names the file that
runner takes; macOS arm64 at the app's floor (`mac.minimumSystemVersion` in
`frontend/electron-builder.yml`), so the hashes make the newer runner install
the floor's wheels — for CPython 3.12, and can be generated from any host. pip's
`--platform` only selects wheels and evaluates environment markers against the
interpreter running it, so the generator runs pip with the target's markers
(`sys_platform`, `platform_system`, `platform_machine`, `os_name`) and then walks
the dependency graph from the declared requirements with them to check the
result. That is what puts `colorama` and `tzdata` in the Windows locks and
`greenlet` in the Linux and Windows ones from a macOS host. A marker on the
running kernel (`platform_release`, `platform_version`) cannot be emulated and
stops the run. The index gives the hash beside each link, except the PyTorch
index for the copy of Jinja2 it serves: the generator downloads and hashes that
file.

backend-ci checks every lock on its own OS, on every pull request, with that
machine's pip and markers (`check_backend_lock.py resolution`): the entrypoint
and `meta/build.txt`, constrained to the lock's versions, resolve to exactly the
lock, and installing the lock selects its locked files. The CUDA locks are
installed by a release tag only; this is what proves them before one.

The dev entrypoints have no lock of their own. backend-ci installs each one
constrained to the versions of the prod lock of its OS (`check_backend_lock.py
constraints` writes them without hashes, which in a constraints file would turn
on hash-checking for the whole install), so the tests run on the versions a
release ships; the dev tools (pytest, ruff, …) are not in a lock and resolve
freely, within the locked versions of what they share with it.

## Key design notes

- **Inference is llama.cpp / MLX, not torch.** torch is only pulled (CPU build)
  by sentence-transformers for the e5 KB embeddings. There is **no torch+CUDA**:
  the CUDA build uses **CPU torch** plus a CUDA-compiled `llama-server` binary
  (built by `scripts/dev/backend/build-llamacpp-cuda-*`). The CUDA toolkit version
  lives in the **binary build**, not in pip — which is why there is a single
  `cuda` entrypoint per OS (no 118/121 split anymore).
- **transformers is pinned once in `base.txt` (5.14.1)** for every platform. The
  floor comes from mlx-vlm 0.6.17 (`transformers>=5.14.0`); it is coupled to
  torch (imports `torch.float8_e8m0fnu`, needing torch>=2.7).
- Fine-tuning deps (peft/accelerate/datasets/bitsandbytes) were removed — the
  feature is unimplemented dead code (see the fine-tuning cleanup issue).

## Usage

```bash
# Dev (with testing/linting tools)
pip install -r requirements/entrypoints/dev/<platform>.txt
# Prod and PyInstaller, exactly the files a release bundles (in a fresh venv)
pip install -r requirements/lock/<platform>-prod.txt --require-hashes --no-deps
```

Or use the platform setup scripts in `scripts/dev/backend/` (they default to prod
in CI; set `INSTALL_TYPE=dev|prod` to force).

## Adding a dependency

- Shared (all platforms) → `meta/base.txt`
- Dev tool → `meta/dev.txt`
- Platform / hardware-specific → the matching `meta/*-specs.txt`
- Build tool (what a release runs to freeze the backend) → `meta/build.txt`

Then regenerate the locks (below) in the same commit; a dev tool alone needs no
regeneration.

## Changing a version, regenerating the locks

Any change to a requirement line of a prod entrypoint, a file it includes, or
`meta/build.txt` (comments and blank lines aside) needs the locks regenerated,
in the same commit:

```bash
python3.12 scripts/dev/lock_backend_requirements.py
py -3.12 scripts\dev\lock_backend_requirements.py      # Windows
```

It needs Python 3.12 (the `python_version` markers are evaluated against it)
with pip, and the network; nothing gets installed. Each lock records a digest of
the requirement lines it was generated from, of the target's platform tags (so
of the macOS floor) and of its own lines, and
`backend/tests/test_requirements_lock.py` fails in backend-ci when they no
longer match — a requirement file or the floor changed, or the lock was edited
by hand — when a declared requirement and its lock disagree, or when a lock is
not sorted.

**The existing locks seed the resolution.** Their versions are passed to pip as
constraints, so regenerating moves only what the change requires: a package
whose declared pin or range no longer accepts its locked version is resolved
again (with whatever it pulls in), and everything else keeps its version and its
file, even when a wheel added since would now be preferred (the generator names
those). A transitive package moves only when you ask:

```bash
# one package (repeatable), e.g. a security fix in a transitive dependency
python3.12 scripts/dev/lock_backend_requirements.py --upgrade-package regex
# everything, to the newest versions that resolve
python3.12 scripts/dev/lock_backend_requirements.py --upgrade
```

When a bump conflicts with a locked transitive version (a new langchain needing
a newer langchain-core), pip fails and names the package: rerun with
`--upgrade-package` for it. The lock diff in the pull request is the list of
everything the bump moves in the shipped app — read it, and look twice at
native packages that change.

Every version here is an exact pin, so bumping one can make the whole set
unsolvable — a library's new release may tighten a range around a sibling that
nobody thought to touch. **Installing into your existing venv does not prove the
set resolves**: pip patches what is already there, quietly upgrading a
transitive dependency to satisfy the package you asked for. The generator
resolves each entrypoint from nothing (`--dry-run --ignore-installed`), so it
fails where CI would.

A dev tool bump (`meta/dev.txt`) needs no lock change. Check it the way
backend-ci installs it, in a throwaway environment:

```bash
python3.12 -m venv /tmp/resolvenv
python3.12 ../scripts/ci/check_backend_lock.py constraints \
    requirements/lock/<platform>-prod.txt > /tmp/resolvenv/lock-constraints.txt
/tmp/resolvenv/bin/python -m pip install --dry-run \
    -r requirements/entrypoints/dev/<platform>.txt \
    -c /tmp/resolvenv/lock-constraints.txt
```

`--dry-run` resolves and prints what it *would* install without building
anything, so it costs metadata rather than gigabytes. Read the resulting
versions: any package that comes out at something other than its pin is a pin
that needs updating in the same commit.
